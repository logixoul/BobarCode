name: bexplore-cleanup
description: Have a strong model explore the whole repo for cleanup opportunities, pick one cohesive improvement from the findings you accept, implement it, and review it with another model via bobar-cli. Use when the user types /bexplore-cleanup <explorer> [reviewer].
---

You are the **author**. This is meant to run unattended (e.g. overnight), so carry on without asking the user anything; they read the result in the morning. `$ARGUMENTS` is `<explorer> [reviewer]`: both are reviewer shorthands from BobarCode's config. The explorer is required; the reviewer for the review loop defaults to `sol`.

1. **Clean tree first.** Run `git status --porcelain -uall` in the repo root. If it prints anything, or fails, stop and tell the user why (e.g. last night's change is still uncommitted): tonight's review would otherwise mix it in. Don't commit anything, at any point.
2. **Explore.** Arm the Monitor tool on `bobar-cli review stream` (in the repo, `timeout_ms` 1800000; arm it first: it waits for the next run that starts). Then run, with Bash `run_in_background: true` (don't poll; you'll be notified), `bobar-cli explore start --reviewer <explorer> --prompt -` with this heredoc on stdin (quote the delimiter: `<<'EOF'`):

   > Explore the entire codebase for opportunities for code cleanup/tightening: changes that would make the code shorter, more elegant, more maintainable or clearer (or more efficient, if that doesn't cost any of those), without changing the product's behavior from the end user's point of view. Report only high-impact ones, at most about 6, most impactful first. For each, give its refs, a rough size (lines touched, files), and the risk of changing behavior. Look explicitly for what could be deleted: dead code, needless layers, duplicated logic. Each finding should stand on its own.

   Some explorers stream their findings to the Monitor as they find them (`### E.<n> …`). Read them as they come, but **edit nothing** during the exploration. `END` means the explorer is done; the background command's output is what counts.
3. **Decide.** When the background command finishes, read its output (first line `STATUS: …`).
   - `findings`: decide each finding honestly: accept it (`fix`) or reject it. A reject needs one concrete sentence naming the path or symbol and why: later explorations see it, so make it recognizable and final (e.g. "`PiReviewer.Args`: the two builders differ in 4 of 7 flags; a shared table is longer than both"). Don't accept something just to have work to do. Then choose **one cohesive change** from the accepted findings: one finding, or several only if they form one change. Keep it small enough for the user to review over morning coffee. If no accepted finding is clearly worth it, choose nothing: that's a good outcome. You may declare verdicts for the GUI first (`bobar-cli review verdicts <run> --fix … --reject …`, display only). Send `bobar-cli explore finish <run> --response -` (foreground) in the format the output shows, with `chosen` listing your choice (or `[]`). On `invalid_response`, fix the JSON and send it again. Edit nothing until it returns `done`.
   - `done` (no findings), `cancelled` or `error`: go to 6.
4. **Implement** the chosen change (no commit). If you chose nothing, skip 4 and 5 (there's nothing to review) and go to 6. Keep it behavior-preserving. Then run the project's full tests and typecheck once and fix what they catch, so the reviewer doesn't spend a round on what tests find.
5. **Review it.** Run the review loop exactly as in the breview skill, without N (if its steps aren't loaded: `cat ~/.claude/skills/breview/SKILL.md`), with `bobar-cli review start --reviewer <reviewer> --explore-run <explore run> --desc -`. The description says: this is a behavior-preserving cleanup from that exploration; which findings it implements (ids and titles) and what changed; and that behavior-preserving means the product behaves the same for the end user, so a behavior change is a bug. Follow breview to its end, including its final check and hindsight. If it ends in `awaiting_decisions`, wait for the user's decisions as breview says (`bobar-cli review wait <run>` in the background) and apply them.
6. **Hindsight on the exploration** (unless it was cancelled): now that you know how its findings held up, send it as the explore output showed (`bobar-cli review hindsight <explore run> --input -`). It rates the explorer. `acceptedWrongly` may list accepted findings, chosen or not.
7. **Report** to the user in a few lines: the explorer's findings with your accept/reject (and reasons for rejects), what you chose and why (or why nothing), what the review loop found and how it ended, both usefulness ratings, and that the change is uncommitted for them to look at and commit.

If you lose track (e.g. after a context reset), `bobar-cli runs` lists recent runs and `bobar-cli review show <run>` prints where one stands.
